# Multi-channel IM Implementation Plan

> Implement inline using executing-plans and test-driven-development; review before release.

**Goal:** 公众号与个人微信复用一个 IM 业务入口，并允许后续通过平台适配器接入其他通道。

**Architecture:** 适配器负责验证来源、解析平台消息和发送；IM 核心使用 channel/account/user/conversation/message 命名空间，负责身份、去重和回复；业务保留已有命令、推广转链、订单与查询页。首个公众号账号保留已有 owner 算法，其他账号/通道独立，禁止昵称自动合并。

**Alternatives:** 各通道复制业务会产生状态漂移；立即引入消息中间件/微服务对当前单实例过重。用户要求抽统一层，因此选择进程内统一入口加受鉴权 HTTP bridge；未来平台可使用SDK/Webhook适配器。

- [ ] 新增 im.py 消息/回复模型及处理入口，core 不依赖 wxauto 或 HTTP。
- [ ] 抽离 mobile 工厂内业务编排，公众号加解密仍留 app.py。
- [ ] 新增可选桥接 API，凭据固定 channel/account，默认关闭；限制长度、请求次数、隐藏异常和密钥。
- [ ] 可选 Windows wxauto 连接器仅接明确配置会话；安全测试优先文件传输助手，Mac 用假客户端验证。发送状态本地持久化，模糊发送状态不自动重发。不跨平台合并用户，不增加支付动作。
